## 🏠 Кейс 1. Разработка тестовой документации для модуля "Комнаты" IoT-платформы Smart Home

Кейс по анализу Swagger-спецификации, составлению матриц тест-дизайна и проектированию чек-листов/тест-кейсов. Тестирование бэкенда (отправка запросов) и сквозных сценариев ролевой модели доступа на стенде не выполнялось из-за лимита времени на сдачу и последующей деактивации окружения.

> ⚠️ **Текущий статус:** Тестовый стенд отключен на стороне заказчика. Проект заархивирован на этапе проектирования документации.

<details>
<summary>📋 Развернуть детали Кейса 1 (Что выполнено по факту в таблицах)</summary>

### 1. Таблицы классов эквивалентности (КЭ) и граничных значений (BVA)
* Проведен детальный разбор полей ввода формы "Добавить комнату" (Название, Описание, Площадь).
* Выделены валидные/невалидные классы эквивалентности (типы символов, кодировки, спецсимволы).
* Проведена проверка числовых и строковых границ на основе требований Swagger (длина строк, лимиты площадей от 1 до 999 999), зафиксированы "серые зоны" для уточнения у аналитика.

### 2. Чек-лист: UI & Функциональность
* Спроектирован и выполнен чек-лист для проверки элементов интерфейса (микро-взаимодействия кнопок, поведение модального окна и логика валидации форм).
* По результатам проверок локализовано и оформлено 7 дефектов фронтенда (включая ввод отрицательных чисел через UI-степперы).

### 3. Тест-кейсы: Комнаты
* Написан комплект из 5 структурированных тест-кейсов для проверки ключевых пользовательских сценариев (валидация сохранения данных при незаполненных обязательных полях, логика работы кнопок-иконок). 

### 4. Проектирование проверок API (Начальный этап)
* Проведен аналитический разбор методов `POST /api/rooms` (добавление) и `GET /api/rooms` (получение списка комнат).
* Спроектирована структура проверок параметров тела запроса (`name`) и параметров фильтрации/пагинации (`limit`).
* Выписаны ожидаемые коды ответов сервера (`200 OK`, `422 Validation Error`, `409 Conflict`) для будущих тестов.

## 📅 Кейс 4. Проектирование тест-дизайна для веб-формы
* **Задача:** Написать чек-лист для проверки календарной логики формы из трех полей ввода (Число, Месяц, Год), выводящей день недели. Ручное тестирование на стенде в рамки задачи не входило.
* **Что сделано:** Спроектировано тестовое покрытие календарной логики. В чек-листе расписаны позитивные сценарии и негативные проверки: високосные года, несуществующие даты (например, 30 февраля) и ошибочные числовые значения.
* **Примененные техники:** Анализ граничных значений, разбиение на классы эквивалентности, попарное тестирование.
* **Результат:** Разработан чек-лист проверок (без проведения фактического тестирования и составления баг-репортов).

## 🔍 Кейс 5. Проектирование тест-кейсов поиска и фиксация наблюдений по бесконечной ленте
* **Задача:** Написать тест-кейсы для проверки перехода пользователя на страницу результатов поиска и провести сессию исследовательского тестирования бесконечной ленты контента (лимит времени 20–30 минут).
* **Что выполнено:** 
  * **Часть 1 (Проектирование тест-кейсов):** Разработан комплект тест-кейсов для проверки отправки поискового запроса разными способами (ввод с клавиатуры, клик, выбор подсказки). Фактическое тестирование на стенде в рамки задачи не входило.
  * **Часть 2 (Исследовательское тестирование):** Проведен свободный осмотр бесконечной ленты подгрузки контента в условиях заданного местоположения. Сформирован список наблюдений с фиксацией потенциальных рисков.
